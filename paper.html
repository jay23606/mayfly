Mayfly: A Browser-First Architecture for Private Media Exchange

An implementation paper

Mayfly Project

Revised July 2026

Abstract

Mayfly is a browser-first progressive web application for ephemeral media, direct messaging, calls, groups, and local-first social features. It combines static client delivery with Supabase-managed identity, access policy, signaling, and constrained fallback storage. The central architectural decision is to send full-resolution live Snaps and call media directly between browsers through WebRTC whenever peers are available, rather than retain that media in application-controlled storage. This paper describes Mayfly’s current delivery paths, distinguishes encrypted fallback delivery from live peer-to-peer delivery, identifies what remains visible to backend services, and records the present reliability and security limitations of the implementation.

Keywords: WebRTC, progressive web application, ephemeral media, client-side encryption, Supabase, browser storage, private messaging.

1. Introduction

Private media systems commonly trade between reliable, server-hosted delivery and minimizing the server’s possession of high-value media. Mayfly explores a browser-oriented position in that trade. The application uses a managed backend, but it does not use that backend as the normal store for full-resolution live Snaps or call streams. When both participants are available, their browsers exchange media over WebRTC.

This is not a claim that Mayfly is serverless. Supabase provides authentication, Postgres records, Row Level Security (RLS), Realtime signaling, private Storage, and Edge Functions. Those services are necessary for account identity, access control, routing, notifications, and a limited offline fallback. The narrower claim is that live full media is normally delivered directly between browsers.

2. System architecture

Mayfly ships as static ES modules with no frontend build step. Capture, image processing, local key handling, encryption and decryption, local history, and live media playback all occur in the browser. The managed backend coordinates participants and persists only the data required by each path.

3. Delivery and messaging paths

Mayfly uses different paths for different feature classes. Privacy claims therefore depend on the path under discussion: a live Snap, an offline media relay, a direct message, and group text do not have identical properties.

3.1 Live Snaps and calls

  1. The sender captures photo or video in the browser; the original remains on the sending device.
  2. Supabase Realtime carries connection signaling, while the application records a small Snap row for routing and receipts.
  3. When the recipient opens the Snap, full media travels over a WebRTC data or media channel between the two browsers.
  4. The recipient renders the media locally and the Snap state advances through delivered, opened, and expired states.

Under this path, the backend does not store the live full-resolution payload. It can still handle account identity, signaling, lifecycle data, timestamps, recipients, a small preview, and a supplied caption.

3.2 Offline media relay

When a recipient is offline, Mayfly offers a deliberately constrained fallback for photos and videos. The browser re-encodes a photo to fit a 50 KB relay budget or accepts an already-compressed video up to 20 MB, encrypts the media once with a random AES-GCM key, and uploads that ciphertext to private Storage. Each recipient device receives a distinct ECDH P-256-encrypted copy of the content key, then decrypts the payload locally with its device-local private key.

The current policy allows one unopened relay per recipient and 100 outstanding relay payloads per sender; a single payload may fan out without duplicating the media ciphertext. It is deleted after all linked recipients claim it, while an unopened relay has a seven-day delivery window. This is a limited encrypted fallback, not a permanent cloud media inbox.

3.3 Direct encrypted text

For 1:1 text, the sender’s browser encrypts the message to the recipient’s public key. The database receives ciphertext, an IV, an ephemeral public key, routing identifiers, and lifecycle metadata. The recipient decrypts locally, retains local thread history, and the application removes the delivery row after ingesting it. Undelivered text expires after seven days.

3.4 Group and live extras

Group membership is persistent and protected by database policy. Open group text uses member-authorized Realtime Broadcast and is intentionally non-durable. Group media, calls, voice clips, files, and in-call games use live peer-to-peer paths. The current implementation should not describe group text as end-to-end encrypted merely because access to its Realtime channel is authorized.

4. Product features and local state

The application has expanded beyond ephemeral media while retaining its underlying delivery model.

  • Capture and expression. Photo and video Snaps, canvas-based photo filters, captions, timers, 24-hour Stories, replies, receipts, and streaks. A small visual preview and Snap metadata are stored to make the inbox usable; the original live media remains on the peer-to-peer path.
  • Conversation and calls. Encrypted 1:1 text, GIFs and stickers via GIPHY, live attachments, voice notes, 1:1 video and voice calls, persistent groups, and group mesh calls. Chess, Geometry Dash, Pac-Man, Pool, Air Hockey, Scrabble, Trivia, Icebreakers, Stack, and Tetris are shared activities within 1:1 calls. Their modules load on demand from the sibling Appmegle deployment.
  • Local-first discovery. Memories are stored in IndexedDB on the current browser and may be deleted there. Clips use a YouTube-backed feed. Saved clips, follows, likes, hidden videos, captions, interests, and the most recent search are browser-local preferences. Shared Clips appear as playable YouTube cards in chat.
  • Profiles and controls. Profiles may display a photo, username, bio, friend count, and join date. Users may hide their profile from Add People; an administrator may enforce that state and prevent new friend requests while the lock is active.

6. Limitations and operational considerations

The architecture has intentional trade-offs. It reduces the amount of full media held by the application’s managed services, but it does not offer the same delivery guarantees as a conventional durable media store.

  • Photo and video Snaps have an encrypted offline relay. Voice notes, files, and live group media remain live-only.
  • There is no configured TURN relay in the current implementation, so calls and peer-to-peer delivery can fail on restrictive or cellular networks.
  • There is no shared multi-device key-recovery model; device-local keys are an intentional constraint.
  • Expired relay cleanup is currently client-triggered rather than performed by a scheduled server job.
  • Server-side moderation of full media is limited because full live media is not centrally retained for scanning.
  • YouTube and GIPHY remain external providers with their own availability, terms, privacy behavior, and content rules.

Client-side cryptography and RLS are useful components, not a complete production security program. A deployment intended for sensitive users should make deliberate decisions about TURN infrastructure, key rotation and recovery, abuse reporting, rate limits, appropriate audit logging, backups, and independent security review.

8. Implementation references

This paper describes the published Mayfly implementation rather than every possible future deployment. The principal paths can be inspected in the source.

  1. core.js handles browser media processing, preview sizing, photo/video relay budgets, Stories previews, and IndexedDB setup.
  2. crypto.js implements the ECDH P-256 to AES-GCM recipient encryption used by relays and direct messages.
  3. rtc.js contains WebRTC signaling and currently has an empty TURN configuration.
  4. chat.js, groups.js, and callapps.js implement conversations, group and live media, calls, and activities.
  5. schema.sql defines tables, lifecycle fields, storage policies, profile privacy rules, and Realtime authorization.
  6. clips.js and memories.js distinguish YouTube-based Clips from browser-only Memories.

9. Conclusion

Mayfly is neither a conventional cloud media inbox nor a purely peer-to-peer system. It is a browser-first social application that uses managed services for coordination while moving high-value live media directly between browsers whenever possible. This posture creates real constraints in reliability, recovery, moderation, and offline delivery. Those constraints are not incidental; they are part of the system’s current privacy and product model.

This is an implementation paper, not a security audit, legal opinion, or guarantee of confidentiality. It was reviewed against the Mayfly source in July 2026.
