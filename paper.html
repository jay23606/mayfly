Implementation note · reviewed July 2026

Private media,
with the browser in charge.

Mayfly is a chat-first PWA that keeps live full-resolution Snaps and calls on a direct browser-to-browser path, while using a small managed backend for identity, policy, signaling, encrypted fallbacks, and notifications.

Mayfly architecture and product boundariesView sourceOpen Mayfly
The precise claim

Mayfly is not serverless. It uses Supabase for authentication, Postgres, Row Level Security, Realtime signaling, private Storage, and Edge Functions. The architectural choice is narrower: when two people are online, the service is not the store for their full Snap or their call media. Their browsers exchange it over WebRTC instead.

01 — System model

Static application. Managed coordination. Direct media.

Mayfly is deliberately browser-first: it ships as static ES modules, has no frontend build step, and treats the browser as the place where capture, encryption, local history, decryption, and live media playback happen.

02 — Data paths

Four different paths, chosen by the feature.

The word “private” means different things for different Mayfly features. The important question is not whether a feature has a server, but what it sends there, in what form, and for how long.

1. Live Snap or call

  1. The sender captures photo/video in the browser. The original stays on the sending device.
  2. Supabase Realtime carries connection signaling; the app records a small Snap row for routing and receipts.
  3. When the recipient opens it, full media travels over a WebRTC data/media channel between the two browsers.
  4. The recipient’s local client renders it and the Snap state advances to delivered/opened/expired.

Result: the backend does not store the live full-resolution payload.

2. Offline photo relay

  1. If a recipient is offline, Mayfly re-encodes a photo only to fit a 50 KB relay budget.
  2. The sender creates an ephemeral ECDH P-256 key, derives AES-GCM encryption for the recipient’s published key, and uploads ciphertext to private Storage.
  3. On return, the recipient’s browser downloads and decrypts that relay with its device-local private key.
  4. One unopened relay per recipient and 100 outstanding relays per sender are allowed; unopened relays have a seven-day delivery window.

Result: a constrained fallback, not a cloud media inbox. Video has no offline relay.

3. Direct encrypted chat

  1. 1:1 text is encrypted in the sender’s browser to the recipient’s public key.
  2. The database receives ciphertext, an IV, an ephemeral public key, and routing metadata.
  3. The recipient decrypts locally; the app keeps local thread history and removes the delivery row after ingesting it.
  4. Undelivered text is capped at ten messages per recipient and expires after seven days.

Result: the server stores ciphertext for the 1:1 message body, not plaintext.

4. Group and live extras

  1. Group membership is persistent and protected by database policy.
  2. Open group text uses member-authorized Realtime Broadcast and is intentionally non-durable.
  3. Group media, group calls, voice clips, files, and in-call games use live peer-to-peer paths.
  4. Games exchange small control/state messages; their modules load on demand when a call starts.

Important: private Realtime authorization is not the same claim as end-to-end encryption for group text.

03 — Product layers

The original delivery model is now a larger product.

Mayfly began around ephemeral media, but its current shape is a browser-native social space. These layers sit on top of the core delivery choices rather than replacing them.

Capture & expressionPhoto/video Snaps, canvas-based photo filters, captions, timers, 24-hour Stories, replies, receipts, and streaks. A small visual preview and Snap metadata are stored to make the inbox usable; original live media stays on the P2P path.
Conversation & callsEncrypted 1:1 text, GIFs/stickers via GIPHY, live attachments, voice notes, 1:1 video/voice calls, persistent groups, and group mesh calls. Shared Chess, Geometry Dash, Pac-Man, Pool, Air Hockey, Scrabble, Trivia, Icebreakers, Stack, and Tetris run inside 1:1 calls; the public Mayfly site currently loads those activity modules on demand from the sibling Appmegle deployment.
Local-first discoveryMemories are stored only in IndexedDB on the current browser and can be deleted there. Clips use a YouTube-backed feed; saved clips, follows, likes, hidden videos, captions, interests, and the last search are browser-local preferences. Clip shares arrive as embedded playable YouTube cards in chat.
Profiles & controlProfiles expose a photo, username, bio, friend count, and join date. A user can hide their profile from Add People; an administrator can force that privacy state and prevent new friend requests while it is locked.
04 — Privacy boundaries

The server is smaller, not blind.

A useful privacy description names what remains visible. Mayfly reduces the backend’s role in full media delivery; it does not make the backend, external providers, or recipients disappear.

Recipient boundary

Neither WebRTC nor encrypted storage can stop a recipient from taking a screenshot, recording a screen, re-sharing media, or showing it to another person. “Ephemeral” describes the application’s delivery and retention behavior, not control over what a recipient does after viewing.

05 — Reliability and safety

The trade is real, and it should stay visible.

What this design gains

  • Full live media is not kept in an application-controlled media library.
  • Offline photo fallback is encrypted before private Storage receives it.
  • Local Memories and Clips preferences do not become backend features by default.
  • The deployable stack is compact: static hosting, browser APIs, and managed backend services.

What it gives up today

  • No offline relay for video Snaps, voice notes, files, or live group media.
  • No configured TURN relay, so calls and P2P delivery can fail on restrictive or cellular networks.
  • No shared multi-device key-recovery model; device-local keys are a deliberate constraint.
  • Expired relay cleanup is client-triggered today, rather than a scheduled server job.
  • Limited server-side moderation of full media, precisely because full media is not hosted there.

External services remain in scope

Clips use YouTube search/embed infrastructure, and GIFs/stickers use GIPHY through Edge Functions. Those providers have their own availability, terms, privacy behavior, and content rules. A Mayfly deployment should be explicit about that.

Security is a system property

Browser crypto and Row Level Security are useful building blocks, not a substitute for production operating practices: a configured TURN service, key-rotation/recovery decisions, abuse reporting, rate limits, audit logs where appropriate, backup policies, and independent review before handling sensitive users or claims.

07 — Audit map

Claims should be traceable to code.

This note describes the published Mayfly implementation, not a claim about every future deployment. The source is short enough that the primary paths can be inspected directly.

  1. core.js handles browser media processing, preview sizing, the 50 KB relay budget, Stories previews, and IndexedDB setup.
  2. crypto.js implements the ECDH P-256 to AES-GCM recipient encryption used by relays and direct messages.
  3. rtc.js contains WebRTC signaling and currently has an empty TURN configuration.
  4. chat.js, groups.js, and callapps.js implement conversations, group/live media, calls, and activities.
  5. schema.sql defines the tables, lifecycle fields, storage policies, profile privacy rules, and Realtime authorization.
  6. clips.js and memories.js distinguish YouTube-based Clips from browser-only Memories.
08 — Conclusion

Mayfly is a practical privacy posture, not a magic word.

Its most distinctive choice is to let the browser carry the highest-value live payloads directly whenever it can, while keeping the backend responsible for the coordination a real social product still needs. The result is neither a conventional cloud inbox nor a purely peer-to-peer toy. It is a browser-first social application with explicit, inspectable limits—and those limits are part of the product.
